# ADR 0005: ノイズの検出に、2回実行とリクエスト時刻への追従を使う

- 状態: 採用
- 日付: 2026-10-02

## 背景

新旧のレスポンスを比べると、互換性とは関係のない差異が必ず出る。採番された ID、生成時刻、トレース ID などで、これらは同じ API を2回呼んだだけでも変わる。これを取り除けないと、本物の差異がノイズに埋もれて、ツールの結果を誰も読まなくなる。

取り除き方には選択肢がある。

1. **利用者が無視するフィールドを列挙する。** 確実だが、API ごとに設定が要る。設定が済むまで結果が読めない
2. **値の形で推定する。** UUID や日時の形をした値は無視する。設定は要らないが、形が日時でも安定している値を見逃す。移行で `created_at` が 9 時間ずれた、という不具合は、まさにこの方法で消えてしまう
3. **LLM に判断させる。** ADR 0004 の理由で採らない

## 決定

値の形ではなく、**値の振る舞い**で判定する。根拠は2つ持つ。

**2回実行(baseline)。** 同じリクエストを旧 API に2回送り、その2つのレスポンスの間で変わったパスを volatile とみなす。Twitter の Diffy が採った考え方である。新旧の比較で同じパスに `VALUE_CHANGED` が出ても、重大度を NONE にする。

**リクエスト時刻への追従(clock)。** 新旧それぞれの値が、その側のレスポンスを受け取った時刻に近いタイムスタンプなら、リクエスト時刻そのものとみなす。

2つ目は Phase 2 の実装中に追加した。デモ API に対して 2回実行だけで試したところ、旧 API の `created_at` が秒単位だったため、2回の呼び出しが同じ1秒に収まり、値が変わらなかった。秒単位のタイムスタンプは珍しくないので、これを拾えないと毎回誤検出が出る。

どちらの根拠も、抑制するのは `VALUE_CHANGED` だけとする。volatile なフィールドでも、型が変わった、フィールドが消えた、という差異は残す。

優先順位は 利用者の `ignore` ルール > 2回実行 > リクエスト時刻。値の形による推定は、重大度を変えないヒントとしてだけ残す。

## 検討した他の案

**2回目の実行を1秒以上遅らせる。** 秒単位のタイムスタンプは拾えるようになるが、実行時間がケース数に比例して延びる。分単位や日付だけのフィールドには効かない。

**値の差が小さければ無視する(許容誤差)。** 「新旧の `created_at` の差が数秒以内なら同じ」とする方法。保存済みのタイムスタンプが数秒ずれている、という本物の不具合まで消してしまう。現在時刻との近さを条件にすれば、保存済みのデータは対象にならない。

**旧 API を3回以上呼ぶ。** 検出の確率は上がるが、リクエスト数も副作用も増える。同じ1秒に収まる問題は解決しない。

## 結果

- 設定なしで、ID・トークン・生成時刻が結果から消える
- 形が日時でも安定している値は、本物の差異として残る(デモの差異 8)
- 旧 API へのリクエストが2倍になる。POST のような副作用のあるリクエストも2回送るので、テスト環境での利用が前提になる。ケース単位で無効にできるようにする
- 時刻の判定には許容幅(既定 5 分)が要る。サーバーの時計がそれ以上ずれている環境では効かない
- 時刻の判定は「言い方」が同じ場合に限る。片方が JST のローカル時刻、片方が UTC であれば、どちらも現在時刻でもノイズにしない
- engine は時計を読まない。受信時刻は入力として受け取るので、同じ入力からは同じ結果が出る
