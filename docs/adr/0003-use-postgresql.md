# ADR 0003: PostgreSQL を使い、ジョブキューも当面 PostgreSQL で持つ

- 状態: 採用
- 日付: 2026-10-02

## 背景

保存するデータは3種類ある。

1. プロジェクト、エンドポイント、ルールなどの設定。関係がはっきりしていて、整合性が重要
2. テストケースの定義と、取得したレスポンス。形が決まっていない JSON
3. 将来、仕様書の埋め込みベクトル

これとは別に、hosted 実行と AI 分析は時間がかかるので、HTTP リクエストの中では実行できない。バックグラウンドで処理する仕組みが要る。

## 決定

データベースは PostgreSQL に一本化する。

- 設定は通常のテーブル、JSON は JSONB 列に入れる
- ベクトル検索が必要になったら pgvector 拡張を足す
- バックグラウンド処理のキューも PostgreSQL で持つ。`runs` テーブルの状態列をキューとして使い、worker が `SELECT ... FOR UPDATE SKIP LOCKED` で1件ずつ取得する

## 検討した他の案

**FastAPI の BackgroundTasks。** 追加のプロセスが要らない。ただし API のプロセスが再起動すると実行中の処理が失われ、失われたことも記録に残らない。外部に接続するコードが API と同じプロセスで動くことにもなる。

**SQS + worker を最初から使う。** 本番で大量に実行するならこちらが正しい。ただしローカル開発に SQS の代替(LocalStack など)が必要になり、MVP の実行量(1回あたり数十件)には過剰。

**Redis + Celery などのタスクキュー。** 実績はあるが、運用する部品が1つ増える。

**ベクトル専用のデータベース。** 仕様書の量は多くても数千チャンクで、pgvector で足りる。データベースを2つ運用する理由がない。

## 結果

- 運用する部品が PostgreSQL 1つで済む。ローカルも `docker compose up` だけで揃う
- ジョブの状態と結果が同じトランザクションで更新できる
- PostgreSQL をキューにする方法は、ジョブが大量になると向かない。worker はジョブの取得部分を分離して書き、SQS への移行はそこだけを差し替えれば済むようにしておく
- JSONB の中身は DB が検証しない。書き込む前に必ず Pydantic で検証する
