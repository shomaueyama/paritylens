# ADR 0001: engine をライブラリとして分離し、実行形態を2つ持つ

- 状態: 採用
- 日付: 2026-10-02

## 背景

最初の構想は「利用者が旧 API と新 API の URL を登録し、ParityLens のサーバーが両方にリクエストを送る」という SaaS だった。この形には2つの問題がある。

1. 刷新の対象になるレガシー API は、たいてい社内ネットワークにある。外部のサーバーからは届かない
2. サーバーが任意の URL に接続する機能は SSRF の入口になる。対策としてプライベートアドレスへの接続を禁じると、1 の API をますます検査できなくなる

つまり、安全にするほど本来の用途から遠ざかる。

## 決定

比較のロジックを `packages/engine` という Python ライブラリに切り出し、それを使う実行主体(runner)を2つ用意する。

- **CLI**: 利用者の環境で動く。社内の API に届き、認証情報は利用者の手元から出ない。こちらを主とする
- **worker(hosted 実行)**: ParityLens 側で動く。ブラウザから実行でき、公開されている API とデモに使う

engine は Web フレームワークにも DB にも依存しない。HTTP を実行する1モジュールを除き、I/O を持たない純粋関数で構成する。

どちらの runner も、実行結果を `RunReport` という同じ JSON で出力する。API はそれを1つの関数で保存する。

## 検討した他の案

**サーバー実行だけにする。** 作るものは少ないが、上の2つの問題がそのまま残る。

**CLI だけにする。** SSRF の問題が消えて最も安全。ただしブラウザから試せなくなり、「登録して実行ボタンを押す」というデモができない。

**利用者のネットワークに常駐するエージェントを置き、サーバーからジョブを配る。** 両方の利点を取れるが、ジョブ配布の API、エージェントの認証、接続管理が必要になり、MVP には重い。必要になったら CLI を拡張して対応できる。

## 結果

- engine を単体でテストできる。DB も HTTP サーバーも要らない
- 実行形態が2つあるので、`RunReport` の形式に互換性を保つ責任が生じる。`schema_version` を持たせて管理する
- SSRF 対策が必要なのは worker だけになる。接続先の検証は `EgressPolicy` として engine に持ち、実行形態ごとに切り替える
- 開発の順序が変わる。engine と CLI を先に作り、DB と Web は後になる
