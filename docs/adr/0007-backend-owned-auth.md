# ADR 0007: 認証をバックエンドで持つ

- 状態: 採用
- 日付: 2026-10-02

## 背景

ParityLens には、認証を必要とする入口が2つある。

- ブラウザ(Next.js の画面)
- CLI(`paritylens run --upload-to`)。CI から実行されるので、ブラウザを介さない

Next.js には Auth.js(NextAuth)という定番のライブラリがあり、Google ログインを数十行で実装できる。ただしその場合、セッションを発行して検証するのは Next.js になる。データを持っているのは FastAPI なので、FastAPI は「Next.js が発行したセッション」を信頼する仕組みを別に持たなければならない。CLI のためのトークン認証は、どのみち FastAPI に要る。

結果として、認証の実装が2か所に分かれる。分かれた認証は、片方だけ直されたり、片方だけ検査が抜けたりしやすい。

## 決定

認証と認可は、すべて FastAPI で行う。

- **ブラウザ**: サーバー側セッション。ログイン時にランダムなトークンを発行し、`HttpOnly; SameSite=Lax` の Cookie で渡す。DB にはトークンの SHA-256 だけを保存する
- **CLI**: API トークン(`plk_` で始まるランダム文字列)。同じく DB にはハッシュだけを保存し、平文は作成時に1回だけ返す。トークンの発行と失効は、ブラウザのセッションでしか行えない
- **ログイン方法**: Google の OpenID Connect(認可コードフロー + PKCE)。ライブラリに任せず、手順を自前で実装し、ID トークンの署名・発行者・宛先・有効期限・nonce を検証する
- **ローカル開発**: メールアドレスを入力するだけの開発ログイン。Google の設定なしで `docker compose up` だけで試せるようにするため。本番設定でこれが有効だと、アプリは起動を拒否する

Next.js はブラウザからの `/api/*` を FastAPI に中継するだけで、セッションの中身を知らない。ブラウザから見るとオリジンが1つなので、Cookie はファーストパーティのまま扱える。

**CSRF 対策**は2段にした。Cookie を `SameSite=Lax` にしたうえで、Cookie で認証された更新系リクエストには、`Origin` ヘッダーが自分自身のオリジンであることを要求する。API トークンによるリクエストは、ブラウザが勝手に付けることがないので対象外。

**テナント分離**は、`repositories/owned.py` に集約した。利用者のデータを取得する関数はすべて `workspace_id` を引数に取り、ID だけで取得する関数は用意していない。他の workspace のデータは、存在しない ID と同じ 404 を返す。

## 検討した他の案

**Auth.js を使い、FastAPI は JWT を検証する。** 実装量は最も少ない。ただし Auth.js のセッション Cookie は暗号化されており、Python 側で復号するには内部仕様に依存する。別途 JWT を発行させる構成にすると、失効(ログアウト)の扱いが難しくなる。

**JWT をセッションに使う(サーバー側に状態を持たない)。** DB を引かずに検証できる。ただしログアウトしても、有効期限までトークンが使えてしまう。失効リストを持てば解決するが、それは結局サーバー側の状態である。この規模では、リクエストごとに1回セッションを引くコストは問題にならない。

**Authlib などの OAuth ライブラリを使う。** 手順を自前で書かずに済む。採用しなかったのは、依存が増えること(HTTP クライアントがもう1つ入る)と、state・nonce・PKCE がそれぞれ何を防いでいるのかを、コードとテストで説明できる形にしたかったため。検証そのもの(JWT の署名検証)は PyJWT に任せている。

## 結果

- 認証・認可のコードが `deps.py` と `repositories/owned.py` に集まる。レビューする場所が決まっている
- テナント分離のテストは、アプリが公開している全ルートを OpenAPI から列挙して行う。ルートを追加すると自動で検査対象になる
- セッションはサーバー側にあるので、ログアウトや強制失効が即座に効く
- OAuth の手順を自前で持つので、その正しさはこちらの責任になる。state の不一致、別の試行の nonce、宛先違い、期限切れ、署名者違い、アルゴリズムのすり替えを、それぞれテストしている
- リクエストごとにセッションを DB から引く。負荷が問題になれば、短時間のキャッシュを入れる余地がある
