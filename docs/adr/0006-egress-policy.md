# ADR 0006: 外向き通信を EgressPolicy で制御する

- 状態: 採用
- 日付: 2026-10-02

## 背景

ParityLens は、利用者が指定した URL に HTTP リクエストを送る。これをサーバー上で行うと、利用者はサーバーを踏み台にして、自分では届かない場所に届くようになる。クラウドのメタデータエンドポイント(`169.254.169.254`)から認証情報を読む、内部ネットワークのデータベースや管理画面に触る、といった攻撃で、SSRF と呼ばれる。

よくある対策は「URL のホスト名を見て、内部アドレスなら拒否する」だが、これだけでは防げない。

- ホスト名は名前にすぎない。`evil.example` の A レコードを `169.254.169.254` にするだけで通り抜ける
- **DNS rebinding**: 検査のための名前解決には公開アドレスを返し、接続のための名前解決には内部アドレスを返す。検査と接続で別々に名前解決をしている限り、防げない
- リダイレクト: 検査を通った URL が、内部アドレスへの 302 を返す
- IPv6 による偽装: `::ffff:10.0.0.1` は IPv6 の姿をした `10.0.0.1` である

一方で、ParityLens の主な用途は社内の API の検査であり、CLI ではプライベートアドレスに接続できなければ意味がない。実行する場所によって、許すべき範囲が違う。

## 決定

接続先の可否を `EgressPolicy` という1つの型にまとめ、3つのモードを持たせる。

| モード | 使う場所 | 許可する範囲 |
|---|---|---|
| `allowlist` | 公開デモ環境 | 設定したホストだけ |
| `public_only` | 不特定の利用者から URL を受け取るサービス | 公開インターネット上のアドレスと、ポート 80 / 443 だけ |
| `permissive` | CLI、ローカル開発 | プライベートアドレスを含む |

どのモードでも、リンクローカルとメタデータのアドレスは拒否する。

検査は2段階で行う。

1. **URL の検査**(`check_url`): スキーム、URL 内の認証情報、ポート、許可リスト
2. **アドレスの検査**(`check_address`): 実際に接続する IP アドレス

2 が本体である。HTTP クライアントの接続処理を差し替え(`GuardedBackend`)、名前解決・検査・接続を1か所で、1回の解決結果に対して行う。

- 名前は1回だけ解決する
- 返ってきたアドレスを**すべて**検査する。1つでも拒否対象があれば、その名前ごと拒否する
- 検査したアドレスに対してソケットを開く。名前では接続しない
- TLS の証明書検証と Host ヘッダーには、元のホスト名を使う

加えて、リダイレクトは追わない(3xx はレスポンスとして記録する)。環境変数のプロキシ設定は読まない。IPv4 を内包する IPv6 アドレス(IPv4-mapped、6to4、Teredo、NAT64)は、中の IPv4 アドレスも検査する。

## 検討した他の案

**URL のホスト名だけを検査する。** 上に書いたとおり、名前と実際の接続先は別物である。

**事前に名前解決して検査し、そのあと普通に接続する。** 実装は簡単だが、検査と接続で名前解決が2回になり、DNS rebinding を防げない。

**外向き通信を専用のプロキシ(Smokescreen など)に通す。** 本番運用ではこれが最も堅い。アプリケーションの不具合があってもプロキシが止める。ただし運用する部品が増えるので、MVP ではアプリケーション内の検査と、ネットワーク設定(セキュリティグループ)の2層にとどめる。

**hosted 実行をやめる。** 最も安全。ブラウザから試せるという利点と引き換えになる。公開環境を `allowlist` にすることで、任意の URL への接続は当面提供しない形にした(ADR 0001)。

## 結果

- SSRF 対策が必要な範囲が、`EgressPolicy` と `GuardedBackend` の2つのモジュールに収まる
- CLI は同じコードを `permissive` で使う。メタデータへの接続だけは CLI でも拒否する
- httpx2 は接続処理の差し替えを公開 API として提供していないため、内部の接続プールを置き換えている。ライブラリの更新で壊れる可能性があるので、ローカルのサーバーに実際に接続するテストで差し替えが効いていることを確認している
- 検査はアプリケーション内で行っているので、検査コードに不具合があれば抜ける。本番ではネットワーク設定でも内部への到達を塞ぐ(設計書 13 章)
- 第三者のサイトへ大量のリクエストを送る踏み台になる、という問題は `public_only` では防げない。一般公開するときは、対象ドメインの所有確認が別に要る
