# ADR 0010: AWS 構成と費用の判断

- 状態: 採用(未適用。Terraform は `validate` まで)
- 日付: 2026-10-02

## 背景

デプロイ先は AWS とし、ECS Fargate と RDS PostgreSQL を使う。これは当初からの前提である。決める必要があるのは、その周辺である。

このプロジェクトは個人のポートフォリオで、利用者は少ない。常時起動する環境に月数万円をかける理由はない。一方で、見た人が構成を読んだときに、なぜそうなっているかを説明できる必要がある。

## 決定

### Web も ECS に置き、ALB でパスによって振り分ける

当初は Web を Vercel に置く案だった。採用したのは、Next.js も Fargate で動かし、ALB が `/api/*` を API に、それ以外を Web に送る構成である。

- ブラウザから見えるオリジンが1つになる。セッション Cookie と Origin の検査は、これを前提にしている
- インフラが Terraform 1つで閉じる。Vercel 側の設定と AWS 側の設定を合わせる作業がない
- 代わりに、Fargate のタスクが1つ増える(月 11 ドル程度)。Vercel の CDN やプレビュー環境は使えない

### NAT Gateway を置かない

Fargate のタスクは、イメージの取得、シークレットの読み取り、ログの書き込みのために、AWS の API に HTTPS で出ていく必要がある。プライベートサブネットに置くなら、NAT Gateway か VPC エンドポイントが要る。

- NAT Gateway: 月 45 ドル程度 + 通信量。この構成のほかの部分すべてと同じくらいかかる
- VPC エンドポイント(ECR ×2、Secrets Manager、Logs): 1つ月 10 ドル程度で、合計は NAT と変わらない

そこで、タスクをパブリックサブネットに置いてパブリック IP を持たせ、セキュリティグループで入口を閉じた。受け付けるのは、ALB からの通信(Web と API)と、worker からの通信(デモ API)だけである。

失ったもの: タスクがインターネットから直接到達可能なアドレスを持つ。セキュリティグループの設定を誤ると、そのまま外に開く。プライベートサブネットなら、設定を誤っても届かない。防御が1層少ない。

RDS はプライベートサブネットに置いた。DB は AWS の API を呼ばないので、これには費用がかからない。

### SSRF 対策をネットワークでも行う

アプリケーションの `EgressPolicy`(ADR 0006)に加えて、worker のセキュリティグループの外向きルールを、デモ API(8000)、DB(5432)、HTTPS(443)に限定した。アプリケーションの検査に不具合があっても、VPC 内のほかのポートには届かない。

443 は閉じられない(LLM のプロバイダーと AWS の API に必要)。ここを絞るには、外向き通信を専用のプロキシに通す必要がある。

タスクロールには権限を一切付けていない。worker が何らかの方法で認証情報を取得しても、それで呼べる AWS の API はない。

### デプロイは GitHub Actions から OIDC で行う

GitHub に AWS のアクセスキーを置かない。ワークフローの実行ごとに GitHub が短命のトークンを発行し、AWS がそれを一時的な認証情報に交換する。引き受けられるのは、このリポジトリの main ブランチのワークフローだけである。

デプロイ用のロールができるのは、イメージの push、タスク定義の登録、サービスの更新だけ。インフラそのもの(VPC、RDS、IAM)は変えられない。インフラの変更は、人が `terraform apply` で行う。

そのため、Terraform は ECS サービスの `task_definition` の変更を無視する(`ignore_changes`)。どのリビジョンが動いているかは、デプロイのワークフローが決める。

### マイグレーションは API コンテナの起動時に行う

API のタスクは1つなので、起動コマンドでマイグレーションを適用してからサーバーを起動する。タスクを2つ以上にするときは、2つが同時にマイグレーションを走らせないよう、デプロイの前に単発のタスクとして実行する形に変える。

### 使わないもの

SQS、S3、CloudFront、Multi-AZ、Container Insights。どれも、必要になったときに足せる。

## 検討した他の案

**App Runner や Lightsail Containers。** 設定が少なく、安い。worker のような HTTP を受けない常駐プロセスや、サービス間の名前解決には向かない。ECS を使うこと自体が学習目的の一部でもある。

**EC2 1台に docker compose。** 最も安い(月 10 ドル前後)。OS の更新、証明書の更新、再起動時の復旧を自分で持つことになる。

**Web を Vercel に置く。** 上に書いたとおり。CDN やプレビュー環境が欲しくなったら、この構成に戻せる。

## 結果

- 月 100〜130 ドル程度(概算)。内訳は `infra/terraform/README.md`
- 常時起動させない運用を想定している。デモのときだけ起動し、終わったら `desired_count` を 0 にする
- ネットワークの分離は、プライベートサブネット + NAT の構成より弱い。その分、セキュリティグループのルールを1つずつ別のリソースにして、読んで確認できるようにした
- **この構成はまだ適用していない。** `terraform validate` と `actionlint` は通っているが、実際の AWS 上での動作は未確認である
